# Markdown正本化設計

## 目的

MyTimes のノート本文は Markdown ファイルを正本とする。SQLite は本文の最終保存先ではなく、表示、検索、メタ情報、同期判定のためのキャッシュとして扱う。

この方針により、アプリを使わなくても Obsidian や任意のエディタでノートを確認、編集できる状態を保つ。

## 正本とキャッシュの責務

### Markdown ファイル

Markdown ファイルはノート本文の唯一の正本である。

- ノート本文の最終保存内容を保持する
- チャット表示と Markdown 編集表示の入力元になる
- アプリ外で編集されても有効な更新として扱う
- アプリの DB やキャッシュが壊れても復元できる対象にする

Markdown ファイルを消さない限り、ノート本文は失われない設計にする。

### SQLite

SQLite は Markdown 正本から再生成できるキャッシュと、アプリ固有のメタ情報を保持する。

- パース済みメッセージ
- ノートファイルのプロジェクト内相対パス
- ファイル更新時刻
- ファイル内容のハッシュ
- パース状態とパースできない本文ブロックの情報
- フォルダ、プロジェクト、アイコンなどアプリ固有のメタ情報

本文内容については SQLite を正本にしない。DB の `messages.content` は Markdown から生成された表示用キャッシュとして扱い、Markdown ファイルの内容と矛盾した場合は Markdown を優先する。

## ノート識別

ノートはプロジェクトディレクトリからの相対パスで識別する。

- UI や DB には原則として相対パスを保持する
- 実ファイルアクセス時のみ、プロジェクトディレクトリと相対パスを結合する
- `..` や絶対パス指定によってプロジェクト外へ出ないように検証する

絶対パスを UI 側の正本として持たせると、プロジェクト移動や同期ディレクトリの変更に弱くなるため避ける。

## DB に保持する情報

後続実装では、既存の `messages` と `folders` を段階的に見直す。初期移行では破壊的な変更を避け、必要な列やテーブルを追加して互換性を保つ。

### ノートファイル情報

ノート単位で以下を保持する。

- プロジェクト ID
- プロジェクト内相対パス
- ファイル更新時刻
- ファイル内容のハッシュ
- 最終読み込み時刻
- 最終パース状態

この情報は、ファイル一覧表示、外部編集検知、DB キャッシュ再生成の判定に使う。

### パース済みメッセージ

チャット表示用に以下を保持する。

- ノートファイルへの参照
- メッセージ本文
- メッセージ時刻
- Markdown 内の出現順
- Markdown 内の範囲情報
- パース元ハッシュ

Markdown 内の範囲情報は、将来的に部分更新や衝突検知を行う余地として保持できる形にする。ただし初期実装では、ファイル全文を読み直してキャッシュを再生成する方式でよい。

### 未分解 Markdown ブロック

チャット形式に安全に変換できない Markdown は削除しない。

- チャット表示では未分解ブロックとして扱う
- Markdown モードでは原文のまま編集できる
- パーサが理解できない本文を DB 更新時に破棄しない

自由な Markdown を無理にチャットカードへ変換すると情報欠落が起きるため、未分解ブロックとして保持する方針を優先する。

## キャッシュ更新タイミング

DB キャッシュは次のタイミングで Markdown から再生成する。

- アプリ起動時
- プロジェクト選択時
- Markdown モードで保存した直後
- チャット投稿で Markdown に追記した直後
- 手動リロード時
- 将来のファイル監視で外部更新を検知した時

初期実装では、起動時と手動リロードの全件再読み込み、保存直後と投稿直後の対象ファイル再読み込みを優先する。ファイル数が増えた場合は、更新時刻とハッシュで変更対象だけを再パースする。

## 書き込み方針

チャット投稿と Markdown 編集では書き込み方式を分ける。

- チャット投稿: 対象 Markdown ファイルの末尾へ追記する
- Markdown 編集: エディタ内容でファイル全体を保存する
- 保存後: 対象ファイルを再読み込みし、DB キャッシュと画面表示を更新する

既存の `export_messages_to_markdown` は DB メッセージから Markdown を全体生成するエクスポート機能であり、Markdown 正本化後の通常投稿経路には使わない。既存データ移行やバックアップ用途に限定し、外部編集済み Markdown を上書きしないようにする。

## 既存データ移行方針

既存ユーザーの `messages` にのみ存在する本文は、初回移行で Markdown ファイルへ書き出す。

1. 既存 `messages.note_path` がある場合は、そのパスに対応する Markdown ファイルを移行先候補にする。
2. `note_path` がない場合は、`created_at` から `YYYY/MM/YYYY-MM-DD.md` を生成する。
3. 移行先ファイルが存在しない場合は、既存メッセージから Markdown を新規作成する。
4. 移行先ファイルが存在する場合は、自動上書きしない。
5. 既存ファイルがある場合は、移行候補を別ファイルに書き出すか、ユーザー確認を挟んで追記する。
6. 移行後に Markdown を読み直し、DB キャッシュを再生成する。

移行処理は一度で完了できることより、既存 Markdown を壊さないことを優先する。

## 後続 issue の判断基準

- `MYT-21`: プロジェクトは実ディレクトリを参照し、ノート探索の起点を `project.directory_path` に寄せる
- `MYT-22`: ファイル探索、読み込み、保存 command はプロジェクト内相対パスを返し、プロジェクト外アクセスを拒否する
- `MYT-23`: パーサと writer は Markdown を消失させず、チャット投稿は追記で実装する
- `MYT-24`: UI は同一 Markdown ファイルをチャット表示と Markdown 編集の 2 形式で扱う
- `MYT-25`: 外部編集は正規の更新として扱い、未保存変更を黙って上書きしない
